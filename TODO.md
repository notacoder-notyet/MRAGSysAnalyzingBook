## 📋 Предложенные задачи — оценка и обоснование

### 1. Семантический кэш частых вопросов — 🟡 **P1**

**Идея:** хранить пары «вопрос → ответ»; новый вопрос сравнивать по косинусной
близости с сохранёнными и при совпадении выше порога отдавать готовый ответ.

**Почему P1, а не ниже.** Это не оптимизация «на будущее», а прямое решение
нашей текущей боли: бесплатные модели на OpenRouter дают ~50 запросов в сутки.
На демо-показе (несколько человек, несколько дней) лимит выедается быстро.
Кэш убирает LLM-вызов целиком — а студенты задают одни и те же вопросы
про функцию потерь и переобучение.

**Что даёт:**
- Латентность: с ~3–5 с до ~50 мс на попадании
- Расход лимитов LLM: падает в разы
- Отдельная метрика `hits` покажет самые частые вопросы

**Как делать:**
1. Таблица `answer_cache(question, embedding, answer, sources, hits, created_at)`
   или отдельная коллекция Chroma
2. На входе: `search(query_vec, top_k=1)` по кэшу
3. Если `score >= CACHE_THRESHOLD` → вернуть готовое, инкрементить `hits`
4. Иначе — обычный путь RAG + запись в кэш

**Риски — важные:**
- ⚠️ **Порог должен быть высоким (0.93–0.97).** При 0.85 «что такое переобучение»
  и «что такое недообучение» схлопнутся в один ответ. Это худший вид бага:
  система уверенно отвечает не на тот вопрос.
- ⚠️ **Инвалидация.** При смене модели эмбеддингов или переиндексации кэш
  недействителен, иначе отдаём ответы по старому корпусу. Нужен `cache_version`.
- ⚠️ TTL/LRU: устаревшие ответы лучше вытеснять.

**Трудозатраты:** ~2–3 часа. **Зависимости:** нет, можно делать сразу.

**Бонус для портфолио:** «semantic caching» — реальный приём из продакшена.

### 2. Гибридный поиск (dense + sparse) — 🟡 **P1**

**Идея:** объединить векторный поиск с лексическим (BM25) через RRF
(Reciprocal Rank Fusion).

**Почему именно нам это нужно.** Аббревиатуры и точные термины (`Focal Loss`,
`MLflow`, `DVC`, `encoder-only`) — слабое место dense-поиска: эмбеддинг
«размазывает» редкий токен по смыслу. BM25 ловит их по точному совпадению.
Методы дополняют друг друга — поэтому в продакшене их комбинируют.

**Что даёт:** рост recall на терминологических запросах. Ожидаю +5–12 п.п.
к Hit@5, но **нужно измерить**, а не предполагать.

**Как делать:**
- **Qdrant**: sparse-векторы нативны — почти бесплатно
  (`sparse_vectors_config` + BM25-вектора при индексации)
- **Chroma**: sparse не умеет → отдельный индекс `rank_bm25` в памяти
  (1034 чанка влезают без проблем)
- Слияние: RRF `score = Σ 1/(k + rank)`, `k=60` — стандарт, устойчив к разным шкалам
- Обязательно `gold_set.py eval` до и после

**Риски:**
- ⚠️ **Двойная индексация** — нужно синхронизировать векторный и BM25-индексы
- ⚠️ Может **ухудшить** результат: BM25 подмешает мусор из сломанных страниц.
  Поэтому строго **после P0**
- ⚠️ BM25 плохо работает на русском без лемматизации: «векторов» и «вектор»
  не совпадут. Нужен `pymorphy2` или `razdel`

**Трудозатраты:** ~4–6 часов. **Зависимости:** делать **после** P0 (парсинг таблиц),
иначе измеряем улучшение на сломанных данных.

### 3. Мониторинг и оркестрация — разбить по ценности

Этот пункт неоднородный: внутри смешаны полезное и переусложнённое.
Оцениваю каждый инструмент отдельно, а не списком.

| Инструмент | Приоритет | Вердикт |
|---|---|---|
| **MLflow** | 🟡 P2 | **Полезно.** У нас есть eval-метрики и меняющиеся параметры (модель, chunk_size, top_k). Сейчас «до/после» сравнивается руками. MLflow даст историю экспериментов — сможем доказать цифрами, что гибридный поиск реально улучшил Hit@5, а не «кажется лучше» |
| **Prometheus + Grafana** | 🟢 P3 | **Умеренно.** Метрики: latency `/api/chat/ask`, доля 429 от LLM, cache hit rate, расход токенов. Но на одном пользователе графики смотреть некому — ценность в демонстрации навыка, не в использовании |
| **Airflow** | 🟢 P3 | **Переусложнение.** Пайплайн — 4 команды, запускаются разово. Airflow ради этого = +сервис, +БД, +DAG-файлы ради `&&`. Если цель — показать навык, `prefect` или `Makefile` дают то же в 20 строк |
| **Docker Swarm** | 🟢 P3 | **Переусложнение.** Один хост, один контейнер — Swarm не даёт ничего |
| **Kubernetes** | 🟢 P3 | **Переусложнение для пет-проекта.** Но если цель — строка в резюме, это самый «продаваемый» пункт. Честно: реальной пользы проекту не несёт |

**Моя рекомендация — прагматичный минимум:**

1. **Docker + docker-compose** — 🟡 **P1**. Это реально нужно: сейчас запуск требует
   `venv`, 5 команд и установки torch (~2 ГБ). `docker compose up` решает задачу
   «показать проект» за минуту. Даёт больше, чем K8s.
2. **MLflow** — 🟡 **P2**. Трекинг экспериментов, польза для eval.
3. **Prometheus + Grafana** — 🟢 **P3**. Только если останется время.
4. **K8s / Swarm / Airflow** — 🟢 **P3**, и **осознанно не рекомендую**.
   Для пет-проекта на одном хосте они создают поддержку, которой никто не пользуется.
   Если нужен «девопс-пункт» в резюме — Docker + CI/CD достаточно,
   а K8s лучше показать в отдельном проекте, где он уместен.

## ✅ ГЛАВНЫЙ ВЫВОД eval — уточнён 07.10.2026

**Прежний вывод «100% провалов — мусорный текст» был артефактом сломанной метрики.**
Метрика `garble_ratio` считала мусором обычные односложные слова («в», «и», «с») и
раздувала показатель до 77% страниц. После исключения валидных односложных слов:

- средняя «мусорность» страниц — **0.056** (не 0.24);
- страниц выше порога 0.15 — **91 из 973** (не 749);
- в провалах **0/8** страниц превышают порог — то есть провалы **не** про мусор.

Что реально сделано и измерено:

1. Модуль `text_clean.py` (NFKC + удаление эмодзи + фильтрация мусорных строк),
   подключён в `pars_pdf.extract_text_from_pdf`.
2. Метрика вынесена в `text_clean.garble_ratio` и исправлена.
3. **Переиндексация очищенного текста подняла Hit@8 с 84.1% → 87.3%**
   (53/63 → 55/63), при сохранении 98% символов.

Приоритеты по фактам:

| Приоритет | Задача | Почему |
|-----------|--------|--------|
| 🟢 Low (было 🔴) | **Парсинг таблиц/схем** (Camelot / OpenCV) | Перестал быть блокером: 0/8 провалов на «мусорных» страницах |
| 🟡 Medium | Разрешить **несколько refs** на вопрос в gold-наборе | Часть «провалов» — верные соседние страницы (напр. 23:1 вместо 23:2) |
| 🟡 Medium | Upgrade эмбеддингов → `BAAI/bge-m3` | Рост recall на семантике |
| 🟢 Low | Reranker (cross-encoder) | Точность на top-k, не recall |

Метрика для контроля: `python retrieval_report.py` (`Hit@k` + средняя «мусорность»).

## 📝 Заметки по архитектуре

**VectorStore интерфейс:**
```python
class VectorStore(ABC):
    @abstractmethod
    def add(embeddings, metadatas, ids): ...
    @abstractmethod
    def search(query_vector, top_k, filter_dict=None): ...
    @abstractmethod
    def delete(ids): ...
    @abstractmethod
    def count(): ...
```

**Конфиг (env / yaml):**
```yaml
vector_store:
  type: "chroma"  # или "qdrant"
  chroma:
    persist_dir: "./data/chroma"
    collection: "lessons"
  qdrant:
    url: "http://localhost:6333"
    collection: "lessons"
```

**Переключение одной строчкой в коде / конфиге.**
